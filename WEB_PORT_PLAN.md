# План портирования ChronoKhryshch в веб

Статус: черновик плана (до начала реализации). Движок выбран — **pygbag**. Площадка — **itch.io** (основная), **GitHub Pages** (альтернатива). Платформа релиза — **только десктоп + мышь** (без тача/мобильных).

---

## 1. Что портируем (техническая сводка)

Игра — **софтверный raycaster** (Wolf3D-подобный) на **pygame 2.6 + numpy**, ~3400 строк Python.

- `src/renderer.py` попиксельно считает пол/потолок/стены/спрайты в numpy-буфер `frame[320×200×3]`, затем `apply_post_processing` накладывает виньетку, глубинное затемнение и десатурацию; финальный массив отдаётся в pygame через `surfarray.blit_array` с апскейлом до 960×600.
- Сцены (`app.py`): меню/сплэш/пауза/уровень/финал, стек сцен, блокирующий цикл `while self.running`.
- Ввод: обзор мышью через `pg.event.set_grab` + `pg.mouse.get_rel`; движение WASD.
- Аудио: `pygame.mixer` (SFX) + `pygame.mixer.music` (музыка), 9 файлов `.wav`.
- Сохранения: `save.json` на диск (`src/save.py`).
- Ассеты: 5.3 МБ (44 текстуры, 9 звуков, 2 шрифта), 5 уровней, i18n ru/en.

## 2. Почему pygbag, а не pyxel

- **pyxel не подходит по модели рендера**: он для ретро-пиксель-арта с палитрой 16 цветов и банками тайлов/спрайтов. У нас полноцветный попиксельный raycaster с текстурами, альфа-блендингом, виньеткой и десатурацией. Порт на pyxel = выбросить `renderer.py`, перерисовать все ассеты в 16 цветов, переписать вывод — это не порт, а другая игра.
- **pygbag** запускает тот же pygame-код в браузере через CPython+WebAssembly (Pyodide-подобный рантайм), с wheel'ами pygame и numpy. Переиспользуется ~95% кода; десктопная сборка (включая PyInstaller `.exe`) продолжает работать из того же дерева.

## 3. Главный риск — производительность

Замер нативного рендер-цикла (CPython 3.13 + numpy 2.5, быстрый CPU), только рендер:

```
разрешение 320×200:
  avg frame: 29.3 ms  → ~34 FPS
  floor/ceiling : 17.5 ms   ← узкое место
  walls         :  8.6 ms
  post-process  :  3.1 ms
```

Нативно игра уже впритык к 30 FPS (поэтому `FPS=30`). В Pyodide/WASM чистый Python ~3–6× медленнее, numpy-операции ~1.5–3×. Прогноз «в лоб» без оптимизаций: **~7–12 FPS**. Поэтому: сперва стабильный запуск, затем — оптимизация рендера (это и есть основной объём проекта). Точное число снимем на PoC.

## 4. Архитектурный принцип: веб-слой — тонкая надстройка

Веб-версия собирается из кода upstream-десктопа **вручную по решению человека**. Чтобы апдейты были дешёвыми (минимум конфликтов при merge), веб-специфика не растекается по общему коду:

- Весь веб-код — в **отдельных файлах** (`web_main.py`, storage-shim, pointer-lock/audio-gesture хелперы). Upstream их не трогает → конфликтов нет.
- Правки в **общих** файлах (`app.py`, `audio.py`, `save.py`) — минимальные и **совместимые с десктопом** (через «если браузер, то…», не форк логики). Тот же код собирается в `.exe`.

## 5. Модель веток

Аналогична десктопной сборке:

- **`web`** — долгоживущая, чистая (аналог `main`). Принимает PR только после подтверждения человеком и с максимально чистым кодом (без лишней грязи и временных комментариев).
- **Рабочие/фичевые ветки** (напр. `claude/pygbag-web-game-port-*`) — вся разработка и PoC здесь. PR в `web` — после ревью и подтверждения.
- `web` ответвлена от производственного состояния (`main`).

## 6. Фазы

### Фаза 0 — Proof of Concept (до серьёзных правок)

Цель — превратить прогноз FPS в факт и снять неизвестности за минимум усилий.

1. Поставить pygbag, собрать игру «как есть» с минимальным async-обёртом.
2. Запустить в браузере один уровень.
3. Замерить **реальный FPS в WASM** (нативный ориентир — ~34 FPS render-only).
4. Проверить: загрузку ассетов, `pygame.mixer` (звук после клика), pointer-lock обзор мышью.

Выход: go/no-go + стартовое число FPS.

### Фаза 1 — Стабильный запуск (приоритет #1; оптимизаций не касаемся)

1. **Async-цикл**: `App.run()` → async с `await asyncio.sleep(0)` после `display.flip()`; отдельный `web_main.py`, десктопный `run.py` без изменений.
2. **Упаковка/предзагрузка ассетов** (5.3 МБ) + экран загрузки; проверить относительные пути `assets/...`.
3. **Аудио под автоплей-политику**: отложить `audio.init()` до первого пользовательского жеста.
4. **Хранилище сохранений**: абстрагировать `save.py` (браузер → IDBFS-синк или `localStorage`; десктоп → файл).
5. **Pointer lock / обзор мышью**: оверлей «кликни, чтобы играть», обработка потери фокуса и Esc (согласовать с паузой).
6. **Страница-обёртка**: `index.html`, заголовок, иконка.
7. **Чек-лист дымового теста** (см. §8).

Выход: публикуемый билд, пусть и не на максимальном FPS.

### Фаза 2 — Оптимизация (только после стабильной Фазы 1)

**Разрешение/качество картинки не трогаем** — оно низкое намеренно (old-school стиль). Кандидаты по убыванию отдачи:

1. **Векторизовать `render_floor_ceiling`** (`renderer.py:45`) — убрать Python-цикл по ~100 скан-линиям (нативно это 17.5 из 29 мс), переписать на один `meshgrid`-проход. Отдельно: вложенный цикл по `floor_tiles` гоняет маски на всю ширину для каждой клетки на каждой скан-линии — переписать на точечную выборку. **Самый большой выигрыш.**
2. **Векторизовать `render_walls` / DDA** (`renderer.py:195`, `_march_column`) — сейчас чистый Python по 320 колонкам; батчить марш лучей / выносить тригонометрию разом.
3. **Предрасчёт постоянных таблиц по колонкам** — смещения углов лучей и направляющие множители в конструктор.
4. **Микрооптимизации numpy** — убрать лишние float64-промоушены и `.astype(int)`, in-place операции, переиспользование буферов.
5. **Развязка частоты рендера и ввода** — ввод/таймеры 60 Гц, тяжёлый рендер реже, если упрёмся.
6. **Последний резерв:** снижение внутреннего разрешения или рендер меньшего числа колонок с горизонтальным апскейлом. Только если 1–5 не вытянули.

Ограничение: **Numba/Cython в WASM недоступны** — рычаг только numpy-векторизация и алгоритмика. Если не хватит — отдельный большой разговор про вынос рендера в WebGL-шейдер.

### Фаза 3 — Публикация

- **itch.io** (основная): HTML5-загрузка через `butler`.
- **GitHub Pages** (альтернатива): статика из `gh-pages`.

## 7. Процесс выкатки обновлений веб-версии (алгоритм для человека)

Решение «пора собирать веб» принимает человек. Критерии и шаги фиксированы.

**Когда собирать (что «значимо»):**
- ✅ новый/изменённый уровень, правки геймплея, рейкастера, физики, взаимодействий;
- ✅ правки ассетов (текстуры/звук), багфиксы, влияющие на игру;
- ⛔ можно пропустить: только-десктопное (PyInstaller/`.exe`), README/комментарии, CI.

**Шаги (ручной прогон):**
1. `git checkout web && git merge main` — подтянуть накопленное из upstream.
2. Разрешить конфликты (при соблюдённой изоляции — редкость, только в общих файлах).
3. Собрать билд pygbag (команда — в `WEB_BUILD.md`).
4. Прогнать чек-лист дымового теста (§8).
5. Опубликовать: `butler push` на itch (или деплой в `gh-pages`).
6. **Трассируемость:** записать в `WEB_BUILD.md` SHA upstream-коммита этого релиза и поставить тег (напр. `web-YYYY-MM-DD`).

Манифест `WEB_BUILD.md` (последний синхронизированный SHA + команда сборки + чек-лист) создаётся в Фазе 1.

## 8. Чек-лист дымового теста

меню → старт игры → обзор мышью (pointer lock) → звук и музыка после клика → движение WASD и столкновения → взаимодействие (E) и заморозка времени (F) → ловушки/урон → пауза и Esc → сохранение и восстановление прогресса/языка/настроек звука → завершение уровня → переход между уровнями → финал.

## 9. Открытые вопросы / решения на будущее

- Если векторизации (Фаза 2) не хватит для играбельного FPS — оценить вынос горячего пути рендера в WebGL-шейдер (большой отдельный проект).
- Точные команды сборки pygbag и деплоя на itch/Pages фиксируются в `WEB_BUILD.md` по итогам Фазы 0–1.
